# Обзор SearXNG и рекомендации по само‑хостингу под Windows

## 1. Что такое SearXNG  
SearXNG — это форк популярного мета‑поисковика **SearX**, полностью открытый (MIT‑лицензия) и ориентированный на конфиденциальность. Он агрегирует результаты из более 30 публичных поисковых систем (Google, Bing, DuckDuckGo, Wikipedia, Reddit и др.), преобразует их в единый интерфейс и предоставляет возможность полной локальной установки без передачи запросов к стороннему серверу[^1][^2].

### Ключевые возможности
- **Мульти‑бэкенд**: подключение к более 30 источникам через HTTP‑API или парсинг HTML.  
- **Настраиваемый UI**: темы, язык (русский включён), возможность отключения JavaScript.  
- **Фильтры конфиденциальности**: поддержка Tor, удаление идентифицирующих заголовков, опция «без‑коокиев».  
- **Кеширование**: SQLite‑база по умолчанию, возможность переключения на PostgreSQL/Redis.  
- **Расширения**: плагины‑модули, настройка через YAML‑файл `settings.yml`.  

## 2. Архитектура SearXNG  

```
┌───────────────────────┐
│  HTTP‑сервер (Flask)   │
│  + Jinja2‑шаблоны      │
└───────────┬───────────┘
            │
   ┌────────▼─────────┐
   │  Модуль “engine” │   ← отвечает за построение запросов к бекендам
   └───────┬───────────┘
           │
   ┌───────▼───────┐
   │  Бэкенды‑провайдеры │  (Google, Bing, Wikipedia, …)  
   └───────┬───────┘
           │
   ┌───────▼───────┐
   │  Кеш (SQLite/Redis) │
   └─────────────────────┘
```

- **Flask** — лёгкий WSGI‑сервер, запускаемый в едином процессе.  
- **engine** — синхронный, но поддерживает `gevent`/`eventlet` для асинхронных запросов.  
- **Бэкенды** — каждый реализован как отдельный Python‑модуль, параметры (таймаут, API‑ключ) задаются в `settings.yml`.  
- **Кеш** — по умолчанию SQLite (файл ≈ 10 МБ), может быть заменён на более масштабируемый PostgreSQL или Redis.  

## 3. Типичные сценарии использования  

| Сценарий | Описание | Почему SearXNG |
|----------|----------|----------------|
| **Личный приватный поиск** | Пользователь ищет в интернете, не оставляя следов. | Полный контроль над заголовками, возможность прокси‑через Tor. |
| **Корпоративный поисковый шлюз** | Организация предоставляет сотрудникам централизованный поиск без раскрытия внутренних запросов. | Само‑хостинг, управление политиками доступа, интеграция LDAP. |
| **Образовательные среды** | Университеты открывают публичный поиск без рекламы. | Бесплатный, легко кастомизировать под бренд. |
| **IoT‑устройства / локальные серверы** | Устройства без браузера запрашивают результаты через API. | REST‑интерфейс, возможность ограничить список бекендов. |

## 4. Преимущества само‑хостинга с учётом ваших приоритетов  

| Приоритет | Как SearXNG помогает | Открытые вопросы |
|-----------|----------------------|-------------------|
| **Максимальная приватность** | Полный контроль над запросами, отсутствие сторонних логов; возможность включить Tor‑выходные узлы. | Требуется настройка Tor‑proxy (можно использовать `torify` в WSL). |
| **Локальная работа на Windows + Intel CPU/GPU** | Работает в любой среде, где есть Python 3.9+. На Windows проще запускать через **WSL2** или Docker. | Прямая работа без WSL — требуется `pywin32` и `NSSM` для службы. |
| **Минимизация зависимости от Python** | Можно собрать исполняемый файл через **PyInstaller** или **Nuitka**, уменьшая необходимость установки интерпретатора. | Полная замена на Go/Zig пока невозможна: ядро и большинство плагинов написаны на Python. |
| **Ресурсы** | При базовой конфигурации: 1‑2 CPU, 512 МБ RAM, ~50 МБ диска (SQLite). GPU не используется (поиск – I/O‑ориентирован). | При большом количестве запросов (> 100 req/s) понадобится асинхронный воркер и более мощный CPU. |
| **Настройка** | Конфигурация через один `settings.yml`. Поддержка TLS через обратный прокси (Nginx, Caddy). | Необходимо обеспечить автоматическое обновление сертификатов (Let's Encrypt). |
| **Варианты деплоя** | **Docker** — образ `searxng/searxng` (мультиплатформенно). **Systemd** — в WSL2 через `systemd`‑доступ или в Linux‑контейнере. **Bare‑metal** — прямой запуск `python -m searx` в виртуальном окружении. | На чистом Windows нет `systemd`; альтернативы: `NSSM` или `srvany`. |
| **Сравнение с альтернативами** | Более гибкая, открытая, легко расширяемая чем **DuckDuckGo**, **Startpage** (закрытые). По сравнению с **YaCy** (P2P) — проще в управлении, но без децентрализованного индекса. | У **YaCy** лучше масштабируемость в крупном кластере; требует Java. |
| **Риски & затраты** | Риски: уязвимости в сторонних API, блокировка IP, устаревшие зависимости. Затраты: время на обновления, небольшие вычислительные ресурсы. | Требуется мониторинг обновлений Python‑зависимостей. |
| **Безопасная конфигурация** | Отключить JavaScript в UI, включить CSP, использовать HTTPS, ограничить доступ по IP, запускать под отдельным пользователем без прав `admin`. | Нужно настроить firewall (Windows Defender) для ограничения исходящих запросов. |
| **Масштабирование** | Горизонтальное масштабирование через Docker‑Swarm/Kubernetes, кеш Redis, Nginx‑балансировщик. | Настройка репликации SQLite → PostgreSQL для масштабирования. |

## 5. Развёртывание на Windows  

### 5.1. Через Docker (рекомендовано)  
```powershell
# Установить Docker Desktop (WSL 2 backend)
docker pull searxng/searxng
docker run -d --name searxng `
  -p 8080:8080 `
  -v C:\Users\Vaz\searxng\data:/etc/searx `
  searxng/searxng
```
- **Плюсы**: изоляция, быстрый rollback, простая миграция.  
- **Минусы**: требуется Docker Desktop (платный в некоторых сценариях).  

### 5.2. Через WSL2 + Systemd (Linux‑подсистема)  
1. Установить Ubuntu в WSL2.  
2. `sudo apt-get update && sudo apt-get install python3-venv git`  
3. `git clone https://github.com/searxng/searxng.git && cd searxng`  
4. `python3 -m venv .venv && source .venv/bin/activate`  
5. `pip install -r requirements.txt`  
6. `./manage.sh run` (или `systemctl enable searxng.service` после создания unit‑файла).  

### 5.3. Нативный запуск без WSL (для продвинутых)  
- Установить **Python 3.9+** (Microsoft Store).  
- Установить **NSSM** (Non‑Sucking Service Manager) и создать сервис, который будет выполнять `python -m searx`.  
- Настроить **веб‑прокси** (например, Caddy) для TLS и CSP.  

## 6. Снижение зависимости от Python  

| Способ | Описание | Оценка трудозатрат |
|--------|----------|-------------------|
| **PyInstaller / Nuitka** | Сборка единого исполняемого файла (`searx.exe`). Уменьшает необходимость в отдельном виртуальном окружении. | Средний: 1‑2 ч. (только сборка). |
| **Контейнер‑фасад на Go** | Создать небольшой Go‑прокси, который просто перенаправляет запросы к уже работающему SearXNG‑контейнеру. | Высокий: требует разработки собственного API‑gateway. |
| **Переписывание ядра на Go/Zig** | Полный перенос `engine` и бэкендов в Go/Zig. | Необходимо значительные ресурсы (много недель), не рекомендуется без веской причины. |
| **Использовать уже готовый Go‑форк** | На момент написания нет полностью совместимого Go‑форка. | Ожидание сообщества. |

**Вывод:** полное исключение Python почти невозможно без кардинального переписывания проекта. Для вашего случая целесообразнее собрать исполняемый файл и запускать в изолированном окружении.

## 9. Потенциальные риски и затраты на обслуживание  

1. **Уязвимости в сторонних API** – если один из бекендов изменит структуру ответа, SearXNG может «сломаться» до выпуска патча.  
2. **Блокировка IP** – частый запрос к Google/Bing может привести к временным блокировкам; рекомендуется использовать прокси/Tor.  
3. **Обновление зависимостей** – Python‑пакеты (Flask, Jinja2) регулярно получают security‑апдейты; автоматизация через CI/CD (GitHub Actions) рекомендуется.  
4. **Логи и GDPR** – даже локальные логи могут содержать персональные данные; необходимо обеспечить их шифрование и очистку.  
5. **Стоимость эксплуатации** – практически нулевая (домашний ПК), но при масштабировании (многотысячные запросы) потребуется отдельный сервер/VM.  

## 10. Рекомендации по безопасной конфигурации  

1. **HTTPS** – разместить SearXNG за обратным прокси (Caddy/Nginx) с автоматическим сертификатом Let’s Encrypt.  
2. **CSP & X‑Content‑Type‑Options** – включить в заголовках, чтобы предотвратить XSS.  
3. **Отключить JavaScript** в UI (опция `use_default_locale: false`, `enable_http_referrer: false`).  
4. **Tor‑backend** – добавить в `settings.yml`:
   ```yaml
   tor_proxy:
     url: socks5://127.0.0.1:9050
   ```
5. **Ограничить доступ** – firewall правило, разрешающее только локальные IP (127.0.0.1) или определённый диапазон.  
6. **Запуск под непривилегированным пользователем** – в Docker укажите `user: 1000:1000`.  
7. **Регулярный бэкап `settings.yml` и SQLite** – хранить в зашифрованном архиве.  
8. **Мониторинг** – Prometheus‑экспортёр (можно включить через `searxng-exporter`) для слежения за запросами и нагрузкой.  

## 11. Масштабирование для продакшн‑окружения  

| Шаг | Действие | Инструменты |
|-----|----------|--------------|
| **1. Кеширование** | Переключить SQLite → Redis (быстрее, распределено). | `redis-server`, `redis-py`. |
| **2. Параллелизм** | Запустить несколько воркеров Flask (Gunicorn) с `--workers 4`. | `gunicorn -w 4 -b 0.0.0.0:8080 searx.webapp`. |
| **3. Load Balancer** | Nginx/LB перед несколькими контейнерами. | `upstream searx { server 10.0.0.1:8080; server 10.0.0.2:8080; }`. |
| **4. Авто‑скейлинг** | Docker‑Swarm или Kubernetes (Deploy‑replicas). | `docker service scale searxng=3`. |
| **5. Обновление без простоя** | Rolling‑update через Docker/K8s. | `docker service update --image searxng/searxng:latest searxng`. |
| **6. Защита от DDoS** | Rate‑limit в Nginx (`limit_req_zone`). | `limit_req_zone $binary_remote_addr zone=one:10m rate=5r/s`. |
