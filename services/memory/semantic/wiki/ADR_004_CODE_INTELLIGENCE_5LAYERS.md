# ADR-004: 5-Слойный Code Intelligence SuperGraph Engine в Vazus OS

* **Статус**: ПРИНЯТО (Согласовано с пользователем через `/grill-me`, август 2026)
* **Контекст**: Кодовая база `C:\vazus` требует замкнутого контура анализа, динамического рентгена, предотвращения деградации и формально верифицированной автономной оптимизации кода.

---

## 1. Контекст и Проблематика

Существующие инструменты анализа кода страдают от изоляции:
* Статические анализаторы (SCIP/AST) не знают, что реально вызывается в рантайме, и порождают ложные тревоги.
* Профайлеры (viztracer/pyinstrument) создают тяжелый оверхед на диске Windows и не видят общей структуры модулей.
* LLM-рефакторинги склонны к галлюцинациям, удалению динамического диспатча и нарушению граничных инвариантов.

---

## 2. Принятое Решение: 5-Слойный Симбиоз

Мы внедряем единую 5-слойную архитектуру, где каждый инструмент выполняет строго отведенную роль:

### Слой 1 — Статическая топология и граф вызовов
* **Движки**: `codebase-memory-mcp` (cbm v0.10.x Windows x64) для openCypher BFS-обходов (`trace_path`, `detect_changes`) + `CKB` (SCIP) для компиляторно-точной типизации.
* **Шина данных**: Узлы графа синхронизируются с `kg_nodes` и 768D векторным пространством (Gemini Embedding 2 / Gemma 300M) в `vazus.db`.
* **Сжатие**: `ASTRepoMapper` выполняет PageRank-бисекцию контекста для удержания бюджета до 1800 токенов.

### Слой 2 — Динамический рантайм-рентген и телеметрия
* **Основной движок**: Байткод-мониторинг `sys.monitoring` (PEP 669, Tool ID 3) в Python 3.12+. Оверхед < 8%, потоковая запись `(caller, callee, hit_count, latency)` в память без тяжелых JSON на диске.
* **По требованию**: `pyinstrument` / `viztracer` для точечного профилирования горячих циклов.
* **Эволюция зависимостей**: `UpstreamScanner` отслеживает обновления библиотек (`site-packages` AST + changelogs) для генерации миграций на оптимизированные API.

### Слой 3 — Детерминированные AST-трансформации (Codemods)
* **Иерархический роутер**:
  1. *Tier 0 (5 мс)*: `Ruff --fix` (F401, F841, UP) — мгновенная санитария импортов и переменных.
  2. *Tier 1 (30 мс)*: `ast-grep` (`sg`) — структурный паттерн-матчинг и AST-замены на уровне репозитория.
  3. *Tier 2 (100 мс)*: `GritQL` (`@biomejs/gritql`) — контекстные декларативные миграции API (`where`).
  4. *Tier 3 (Точный CST)*: `LibCST` — Python-трансформеры с сохранением 100% комментариев и форматирования.

### Слой 4 — Контур 6-уровневой верификации и безопасности
* **Песочница**: Эфемерный Git Worktree под защитой Win32 Job Object (лимит RAM, блокировка сети).
* **Формальное доказательство**: `SMT Z3 Equivalence Prover` ($\forall x: f_{new}(x) == f_{old}(x)$) с извлечением точных контрпримеров.
* **Жюри**: Concordia 3-Agent Multi-Perspective Jury (Архитектор + Кодер + Верификатор) $\ge 66\%$ голосов.
* **Circuit Breaker**: Ограничение $\le 5$ функций / 150 строк за одну эпоху оптимизации.

### Слой 5 — Самообучающаяся память и эволюция
* **Реестр успехов**: Фиксация оптимизаций в Karpathy Wiki и `vazus.db` как `VERIFIED_FACT`.
* **Адаптивный Whitelist**: При сбое верификации или обнаружении динамического диспатча символ заносится в `_PROTECTED_WHITELIST` для предотвращения повторных попыток удаления.

---

## 3. Математические Гарантии Безопасности

Кандидат на удаление/модификацию формируется по строгой формуле:
$$C_{candidate} = \Big( C_{static\_0ref} \;\cap\; C_{dynamic\_0hit} \Big) \;\setminus\; \mathcal{W}_{protect}$$

Где $\mathcal{W}_{protect}$ включает:
1. Функции с динамическим диспатчем (`getattr`, `globals()`, `importlib`).
2. Декораторы фреймворков (`@app.get`, CLI-команды, `@field_validator`).
3. Специальные методы протоколов Python (`__*__`).
4. Публичные интерфейсы (2-фазное устаревание `@deprecated`).
