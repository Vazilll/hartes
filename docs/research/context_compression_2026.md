# Контекст-компрессия и контекст-инжиниринг для длинных AI-сессий (2025–2026)

> Подготовлено: 17.08.2026. Цель — как максимально долго и эффективно работать с сильными/дорогими LLM
> (Claude Opus 4.8, GPT-5.6 Sol и т.п.) в длинных сессиях агента, не упираясь в лимиты контекста, цены
> и ограничения провайдера/роутера. Все ключевые утверждения снабжены URL источников.

---

## 0. Резюме для практика (TL;DR)

1. **Компакция (compaction) — первый и главный рычаг.** Anthropic прямо называет её «первым рычагом контекст-инжиниринга»: пересказ истории при приближении к лимиту окна и перезапуск нового контекста на основе сводки. Сопровождается заметным приростом качества длинных агентских запусков ([источник 1](#s1)).
2. **Контекст — конечный ресурс.** Исследования 2025 г. показали «context rot»: способность модели точно использовать информацию падает по мере роста числа токенов в окне, даже если данные технически доступны (Chroma, июль 2025; Anthropic, сентябрь 2025) ([источник 1](#s1), [18](#s18)).
3. **Файловая память (structured note-taking) почти бесплатна и сохраняется между сессиями.** Паттерн NOTES.md / PROGRESS.md / CLAUDE.md (аналог «initializer agent» в Claude Code 2.0) — самый надёжный способ не терять нить на длинных горизонтах ([источник 1](#s1), [6](#s6)).
4. **Субагенты изолируют «грязный» контекст.** Поиск по кодовой базе/интернету выполняется в субагенте, а в главный контекст возвращается сжатый итог (1–2 тыс. токенов). Разделение ответственности — главный приём масштабирования ([источник 1](#s1), [2](#s2)).
5. **Удаление старого tool-output (context eviction) освобождает 30–60% окна.** В Claude Developer Platform это оформлено как API context editing (вставка/замена/удаление в окне, автоочистка) и даёт до +29% к агентной производительности в длинных запусках ([источник 3](#s3)).
6. **Сторонняя prompt-компрессия (LLMLingua, ICAE, xRAG и др.) — зрелая область, но применяется точечно** (RAG-подгрузки, большие документы), а не для кода и не в реальном времени; на 2026 г. появляются сквозные компрессоры-бэкенды (LCLM, 1:4–1:16) ([источник 21](#s21), [29](#s29)).
7. **Memory-системы (mem0, Letta/MemGPT, Zep/Graphiti, LangMem) решают задачу памяти между сессиями**, а не внутри одной сессии; лучший практический результат даёт гибрид: файловая память + (опционально) граф/Zep-подобная система для фактов и предпочтений ([источники 9–17](#s9)).
8. **Для пользователя с роутером + лимитами на длинные сессии** главное — держать каждую отдельную сессию короткой: работа фазами с артефактами-сводками между ними, активная ручная компакция до заполнения окна, минимальный «мусор» (логи, сырые выводы) в контексте.

Руководство Anthropic прямо предупреждает: «контекст — критический, но конечный ресурс» ([источник 1](#s1)).

## 2. Техники сжатия контекста

### 2.1. Компакция (compaction / summarization-based)

**Суть:** при приближении к лимиту окна история (включая tool-вызовы, ошибки, промежуточные результаты) передаётся модели с просьбой сжать в краткую сводку; сессия перезапускается с новой сводкой в начале.
- Anthropic определяет компакцию как «дистилляцию содержимого окна с высокой точностью» и первый рычаг долгосрочной связности агента. В Claude Code она реализована так: история передаётся модели для суммаризации «наиболее критичных деталей», сохраняются архитектурные решения, нерешённые проблемы и основное направление работы; пользователь может вызвать вручную (`/compact`) или дождаться авто-компакции при приближении к лимиту окна ([1](#s1), [7](#s7), [8](#s8)).
- **Порог срабатывания:** в CLI-агентах авто-компакция включается при заполнении окна почти полностью (порог настраивается; предупреждения начинаются раньше). Практическая рекомендация — компактить вручную при ~70–80% заполнения, не дожидаясь авто-срабатывания (сводка получается спокойнее и полнее).
- **Лучшая практика сводки:** структурированный формат (что сделано, текущее состояние, незакрытые вопросы, следующие шаги, ключевые артефакты/пути) — структурированные сводки переживают перекомпакции заметно лучше свободного пересказа.
- **Риски:** потеря деталей (особенно точных чисел, точных путей, формулировок требований). Митигация — дублировать критичные факты в файлы (см. §2.4 и §4).

### 2.2. Rolling window / sliding window

**Суть:** в контекст попадают только последние K сообщений (или последние N токенов), всё старое отбрасывается без сводки.
- Примеры: урезание истории до последних N сообщений в чат-приложениях; «attention sink»-подходы для стриминга (Efficient Streaming Language Models, ScrumLMs и т.п. — направление 2023–2025).
- **Когда работает:** только для задач без длинных зависимостей (простой чат, разовые вопросы). Для разработки — не годится как единственный механизм.
- **Практическое применение:** как «эвикция» старых tool-выводов, а не всей истории.

### 2.3. Context eviction (очистка/удаление части контекста)

**Суть:** удалять из окна то, что больше не нужно: старые tool-результаты, завершённые подзадачи, большие логи, длинные фрагменты кода, уже применённые правки.
- Anthropic: «очистка результатов инструментов» — один из трёх базовых приёмов (компакция + заметки + эвикция), недавно оформлена как функция платформы ([1](#s1), [3](#s3)).
- В агентах: команды `/clear`, `/rewind`, а также новый **API context editing** (см. §2.5), который позволяет программно удалять/заменять сообщения прямо в окне.
- **Эффект:** удаление старых tool-выводов освобождает обычно 30–60% окна; «убирает шум» — модель меньше отвлекается на устаревшие данные.
- **Риск:** если удалённое понадобится позже — потеря. Митигация: перед эвикцией выжимать суть в файл/заметку.

### 2.4. Структурированные заметки (structured note-taking / agentic memory)

**Суть:** агент регулярно пишет заметки-состояния во внешний файл (NOTES.md, PROGRESS.md, CLAUDE.md, memory-файлы), которые по мере необходимости подтягиваются обратно в окно.
- Anthropic: «простой паттерн — агент ведёт NOTES.md — позволяет отслеживать прогресс в сложных задачах с минимальными накладными расходами» ([1](#s1)).
- В Claude Code это оформлено как иерархия CLAUDE.md (memory + rules) и **авто-память** (`auto memory`, включена по умолчанию): важные факты о проекте автоматически сохраняются и подгружаются в начале сессии; управление/просмотр через `/memory` ([6](#s6)).
- В Claude Code 2.0 — «initializer agent»: отдельный агент оставляет структурированные сводки-артефакты для следующих сессий — это официальный паттерн борьбы с «амнезией агента» между сменами работы ([38](#s38)).
- **Это самый дешёвый и самый живучий механизм долгосрочной памяти:** переживает компакции, смены сессий и модели.

### 2.5. Context editing API (вставка/замена/удаление в контекстном окне)

**Суть:** провайдерский API (Claude Developer Platform, ноябрь 2025) позволяет редактировать содержимое окна: заменять сообщение, удалять сообщение, вставлять новые в середину истории, а также чистить старые инструментальные результаты.
- Особенности: работа с «входными» токенами (original_input_tokens), auto-clear — автоматическая очистка старых tool-результатов при приближении к порогу; комбинируется с memory-инструментом: перед очисткой модель получает предупреждение сохранить важное в память ([3](#s3)).
- **Цифра от Anthropic:** контекст-редактирование/эвикция в длинных агентских запусках даёт **до +29% агентной производительности** (по внутренним оценкам; приводится в контексте Claude Code 2.0) ([38](#s38), [3](#s3)).
- Аналоги: у OpenAI в Responses API — управление контекстом через `previous_response_id` (переиспользование предыдущего ответа как входного контекста без повторной отправки всей истории), у Gemini — context caching и файлы-контекста ([23](#s23)).

### 2.6. Prompt compression (сторонние компрессоры промптов)

Зрелое научное направление (2023–2026), в основном для RAG-подгрузок и больших документов, не для кода:

| Метод | Суть | Сжатие | Источник |
|---|---|---|---|
| **LLMLingua** (EMNLP 2023) | удаление несущественных токенов по оценке языковой модели | до ~20x | [20](#s20), [21](#s21) |
| **LongLLMLingua** (ACL 2024) | то же + приоритизация релевантных запросу частей; +21.4% к RAG-качеству при 1/4 токенов | 4–20x | [22](#s22) |
| **LLMLingua-2** (ACL 2024) | дистилляция + токен-классификатор (быстрее, вернее) | 2–10x | [23](#s23) |
| **ICAE / In-context Autoencoder** (ICLR 2024, Microsoft) | «мягкое» сжатие: длинный контекст → 128 memory-слотов (обучаемые эмбеддинги), ~1% доп. параметров | 4x | [24](#s24) |
| **xRAG** (NeurIPS 2024) | экстремальное сжатие извлечённых документов до 1 токена | до сотен x | [26](#s26) |
| **Adapting LMs to compress contexts** (Apple/Princeton, Chevalier et al. 2023) | дообучение модели на генерацию сводок, пригодных для переиспользования другими ответами | 4–8x | [27](#s27) |
| **Nugget 2D** (JHU, 2023) | динамическое контекстное сжатие для decoder-only моделей | — | [30](#s30) |
| **LCLM / End-to-End Context Compression at Scale** (2026) | сквозные латентные компрессоры 1:4/1:8/1:16; агент «просматривает» сжатый контекст и разворачивает нужные фрагменты; лучше парето-граница качества/скорости/памяти | 4–16x | [29](#s29) |

**Практические выводы:**
- Готовые библиотеки: `llmlingua` (PyPI), LangChain `ContextualCompressionRetriever` (обработка результатов RAG до подачи в модель) и LlamaIndex `ContextCompressor` ([19](#s19), [31](#s31)).
- Для повседневной агентской работы (код, инструменты) программная компрессия промптов **не рекомендуется**: ломает синтаксис, пути, точные идентификаторы; выигрыш в токенах не окупает потерю точности.
- Наиболее перспективное применение на 2026: сжатие больших загружаемых документов и «снапшотов» состояния проекта для старта новой сессии.

### 2.7. KV-cache / контекст-кэширование (провайдерская опция)

- **Anthropic prompt caching:** кэширование повторяющихся префиксов (~10% цены на cached tokens, TTL 5 мин) — экономия до 90% на входных токенах при длинных стабильных префиксах ([4](#s4)).
- **OpenAI:** автоматическое кэширование входных токенов (>1024 ток., TTL 5–60 мин) со скидкой ~50% на cache hits ([23](#s23)).
- **Gemini:** контекст-кэширование с TTL до 1 часа и большими скидками ([36](#s36)).
- **Для пользователя через роутер:** зависит от того, прокидывает ли роутер `cache_control`/кэш-параметры и делится ли экономией; если нет — экономия на кэше недоступна, и компакция становится основным инструментом снижения цены.

## 3. Memory-системы для агентов

Разделение: память **внутри** одной сессии (контекст) vs память **между** сессиями (хранилище). Memory-системы решают вторую задачу.

| Система | Архитектура | Фишки | Лицензия | Источники |
|---|---|---|---|---|
| **mem0** | извлечение фактов LLM → эмбеддинги + векторное хранилище; ADD-only конвейер, entity linking, top-200 retrieval | 63k+ звёзд, работает со 100+ слоями хранения (Chromadb, PG, Redis, Qdrant…); платформенная версия сильнее OSS | Apache 2.0 | [9](#s9), [10](#s10) |
| **Letta (f.k.a. MemGPT)** | агент-ОС с иерархией памяти: core memory + archival + recall, self-editing памяти | мемы-иерархия как в ОС, архивация в векторную память, инструменты-«память»; V2 (letta-code) — активная разработка | Apache 2.0 | [11](#s11), [12](#s12) |
| **Zep + Graphiti** | **temporal knowledge graph**: битемпоральный граф сущностей/фактов, гибридный поиск (граф + вектор), сборка «токен-эффективного» контекста за <200 мс; Context Lake для долгого хранения | enterprise-фокус; Graphiti — OSS ядро | Zep: proprietary/cloud, Graphiti: Apache 2.0 | [13](#s13), [14](#s14), [15](#s15) |
| **LangMem (LangChain)** | SDK для управления памятью в LangGraph: memory-инструменты для агента «в горячем пути», фоновый memory manager, профили пользователей, семантическая память | интеграция с LangGraph Long-term Memory Store | MIT | [16](#s16) |
| **Microsoft GraphRAG** | RAG по графу знаний: кластеризация сущностей (Leiden), «community summaries», query-фокусные обзоры | хорошо для корпоративных корпусов/документов; тяжёлый (индексация дорогая) | MIT | [17](#s17) |
| **Простая файловая память** (CLAUDE.md, NOTES.md, GEMINI.md, AGENTS.md, memory.json) | файлы-инструкции и файлы-заметки, подгружаемые в начало сессии | нулевые накладные расходы, версионируется git'ом, читается человеком | — | [6](#s6), [25](#s25), [34](#s34) |

Исследовательская база: MemGPT предложил концепцию «LLM как ОС» с выгрузкой памяти (arXiv:2310.08560); обзор механизмов памяти агентов — arXiv:2404.13501 ([28](#s28), [32](#s32)).

**Практическая рекомендация для Hermes-подобного агента:** начать с файловой памяти + ручных сводок (это закрывает 80% потребностей), затем по мере необходимости добавить mem0 (простейший self-host) или Zep/Graphiti (если нужны сущности/граф фактов и бизнес-данные). Тяжёлый GraphRAG — только для больших стабильных корпусов.

## 4. Паттерны длинных сессий

### 4.1. Субагент-декомпозиция (изоляция «грязного» контекста)

- Главный агент держит план и синтезирует; субагенты выполняют глубокую техническую работу/поиск в **своих чистых окнах** и возвращают только сжатый итог — обычно 1–2 тыс. токенов. Подробный контекст поиска остаётся изолированным в субагентах ([1](#s1)).
- Anthropic применили это в своей multi-agent исследовательской системе и зафиксировали «существенное улучшение против single-agent» на сложных исследовательских задачах ([2](#s2)).
- **Когда:** исследование кодовой базы, веб-поиск, чтение больших файлов, параллелизуемые подзадачи.
- **Цена:** доп. вызовы (латентность, токены на инструкции субагента) — окупается, если подзадача «дорогая» по контексту.

### 4.2. Триггеры суммаризации (summarization triggers)

- **По заполнению окна:** компакция при 70–80% (вручную) или авто (90–95% или порог провайдера).
- **По смене фазы/задачи:** перед переходом к новой подзадаче — сводка завершённого блока в NOTES.md (паттерн checkpoints).
- **По «возрасту»:** исследования контекст-рота показывают деградацию точности с ростом длины контекста — не держать в окне «хвосты» давно сделанного (старые tool-выводы чистить немедленно) ([18](#s18), [1](#s1)).
- **По важности:** критичные факты (точные имена, пути, версии, решения) — в начало окна (файл-память), т.к. модели лучше используют начало и конец окна («lost in the middle», arXiv:2307.03172) ([33](#s33)).

### 4.3. Tool-call-heavy vs context-heavy сессии

- **Tool-call-heavy** (много вызовов инструментов): риск засорения окна стенами JSON/выводов. Правила: (а) усекать вывод больших tool-результатов на лету (head/n строк, спец-поля), (б) писать большие результаты в файлы и возвращать пути, (в) эвиктировать отработанные tool-вызовы (context editing / /clear), (г) при работе с набором файлов — индексировать (grep/tree) вместо чтения файлов целиком.
- **Context-heavy** (длинные тексты, документы): не загружать целиком — использовать чанки/RAG, сводки по главам, вопросы к документу через субагента; применять prompt-компрессию (§2.6) для подгружаемых кусков.
- Для больших моделей (Opus 4.8, GPT-5.6 Sol) «дешёвым» является добавление токенов в начале (системный промпт/память), но каждое добавление ускоряет контекст-рот — поэтому структурируйте, а не накапливайте.

### 4.4. Планирование и артефакты между сессиями

- Паттерн Claude Code 2.0: **initializer agent** пишет structured handoff-документ; следующая сессия стартует с него, а не с нуля ([38](#s38)).
- Для вашего сценария (лимит на длинные сессии у роутера): разбивайте проект на фазы, каждая фаза — отдельная короткая сессия, между фазами — файл-артефакт (цель, сделано, состояние, следующие шаги, известные проблемы). Каждая сессия стартует со сводки предыдущей.

## 5. Что используют топовые CLI-агенты (2025–2026)

### Claude Code (Anthropic)
- **Авто-компакция** при приближении к лимиту окна + ручная `/compact`; сводка сохраняет архитектурные решения и незакрытые вопросы ([7](#s7), [8](#s8)).
- **Память:** иерархия CLAUDE.md (user → project → .claude/rules/), AGENTS.md-поддержка, **auto memory** (включена по умолчанию), `/memory` для просмотра/редактирования ([6](#s6)).
- **CLI/настройки:** `--continue` для переноса сессии, `/rewind`, `/clear` (полная очистка — отдельный режим, при котором история не используется), `--resume` список сессий.
- **Context editing API** + предупреждение o приближении к порогу и автосохранение важного в память перед очисткой ([3](#s3)).
- **Claude Code 2.0** (25.11.2025): 1M окно на Max/Team/Enterprise, memory 2.0 (auto-memory), улучшенные субагенты, платформенные агенты ([38](#s38)).
- Гайд по снижению расходов: чистить сессии между несвязанными задачами, подбирать модель под задачу ([8](#s8)).

### OpenAI Codex CLI
- **Статическая память:** AGENTS.md-файлы (в т.ч. codex_AGENTS.md) с инструкциями и правилами; поддержка «свежих» файлов (fresh files) для подсказок о новых файлах.
- Диалоговая сессия держится в окне модели; для длинных работ рекомендуется дробить на чекпоинты, коммитить и начинать новые сессии; есть rolling-подходы сообщества (см. §6) ([34](#s34)).

### Cursor
- Акцент на **анти-загрязнении контекста**: rules, subagents, hooks, skills; индексация кодовой базы вместо загрузки файлов; автозаполнение контекста по релевантности (провайдерское «context engine»); модельная таблица с контекстами (Opus 5 1M, GPT-5.6 Sol 272k и т.д.) ([35](#s35)).

### Gemini CLI (Google)
- 1M-окно, **checkpointing** сессий (сохранение/возобновление), **GEMINI.md** — пользовательские файлы контекста, интеграция с Google Search ground, MCP, нативный вход в агентский хаб [25](#s25).

### Aider (open-source)
- **Repo map** — компактная карта модулей (дерево + описания) вместо загрузки кода; жёсткий лимит контекста; рекомендации «дробить большие файлы»; **/clear и /undo** для сброса истории.

### opencode (open-source, ближайший аналог Hermes)
- Менеджер сессий (`opencode sessions`), флаги `--continue`/`--resume`/`--session`, плагины для кастомизации контекста; динамическое обновление системного промпта; архитектура «fragment -based messages» (для потокового вывода и компактного хранения истории).

## 6. Open-source наработки по компрессии контекста для API

- **microsoft/LLMLingua** (+ LongLLMLingua, LLMLingua-2, SCBench, RetrievalAttention): готовые Python-библиотеки компрессии промптов и benchmarks с позиции KV-cache ([20](#s20), [21–23](#s21)).
- **LangChain / LlamaIndex**: ContextualCompressionRetriever / ContextCompressor (обёртки: LLMChainExtractor, EmbeddingsFilter, LLMLingua) — де-факто стандарт «сжать результаты RAG перед подачей» ([19](#s19), [31](#s31)).
- **ICAE (getao/icae), xRAG, Adapting LMs to compress contexts, Nugget 2D** — исследовательские реализации мягкой/жёсткой компрессии ([24](#s24), [26](#s26), [27](#s27), [30](#s30)).
- **LCLM (2026)** — готовая экспериментальная модель компрессора (1:4/1:8/1:16), huggingface.co/latent-context, github.com/LeonLixyz/LCLM; паттерн «skim & expand» для длинных агентов ([29](#s29)).
- **Сообщество:** скрипты «codex/Claude Code compaction prompts» — эффективные шаблоны сводок для перезапуска сессий; практики «session handoff» (публикации в блогах/репозиториях о переносе состояния между сессиями CLI-агентов).

Ничего готового «встрой и забудь» для коммерческого API-агента пока нет — все работающие решения это комбинация: компакция (своя логика) + файловая память + точечная компрессия для RAG-подгрузок + (опционально) провайдерский кэш/context editing.

## 7. Практические рекомендации для Vaz (Hermes-подобный агент, роутер, лимиты на длинные сессии)

Конкретика под ваш сетап: повседневка — deepseek-v4-flash (дешёвый, большой контекст), тяжёлая работа — claude-opus-4-8 / gpt-5.6-sol (272k+) через agentrouter с лимитом на длинные сессии по контенту.

1. **Сессия = фаза.** Никогда не ведите одну сессию «до смерти». Каждая фаза: цель (1–3 строки) → работа → сводка-артефакт в файле (`session_handoff.md` / `PROGRESS.md`). Новую фазу начинайте со сводки. Это обходит и лимит роутера, и контекст-рот.
2. **Компакция — ваш главный инструмент на Opus/GPT.** Компактить вручную при ~70–80% заполнения окна; сводку делать структурированной (сделано / состояние / открытые вопросы / точные имена и пути / следующий шаг). Перед каждым компактом сбрасывайте критические факты в файл-память.
3. **Всё что можно — в файлы, в контекст — только ссылки.** Вывод инструментов >30 строк обрезайте (head/хвост) или пишите в файл и возвращайте путь. Не грузите логи, сырые JSON, целые файлы — используйте поиск (grep/агентский поиск), деревья, чанки.
4. **Субагенты для «грязной» работы.** Поиск по кодовой базе/интернету, чтение больших документов — в субагентах; в основной контекст — итог 1–2k токенов.
5. **Начните (опционально) файловую память проекта** — аналог CLAUDE.md: пути, команды сборки, конвенции, «что мы строим». Это окупается на каждой следующей сессии.
6. **Не применяйте программную компрессию промптов к коду** (LLMLingua и т.п.) — для кода она ломает точность; применяйте только к загрузке больших текстов/RAG.
7. **Распределение моделей:** черновики, исследования, bulk-задачи — deepseek (дёшево, можно длинно); финальные итерации, тонкий рефакторинг, сложный анализ — Opus/GPT короткими «точечными» сессиями, где каждый токен на счету (малый контекст = меньше цена и меньше риск цензуры).
8. **Если роутер не прокидывает кэш/коном.** Проверьте, поддерживает ли agentrouter prompt caching / cache_control: если нет — для Opus/GPT стратегия «маленькое окно + файловая память + компакция» выгоднее, чем «большое медленно растущее окно».
9. **Против «потери нити» после цензурного обрыва:** держите partage артефактов в репозитории/git (handoff-файлы, ADR, чекпоинты) — любую сессию можно пересобрать за один промпт из артефактов, даже если роутер оборвал связь на середине.

## 8. Сравнительная таблица методов

| Метод | Суть | Экономия токенов | Риски | Сложность | Когда применять |
|---|---|---|---|---|---|
| Компакция (manual / auto) | пересказ истории → новый контекст | 50–90% сразу | потеря деталей при плохой сводке | низкая | всегда, первый рычаг |
| Rolling window | только последние K сообщений | простая, предсказуемая | теряется всё старое | низкая | простые чаты, не для разработки |
| Context eviction (/clear, очистка tool-выводов) | удаление отработавших кусков | 30–60% окна | потеря упоминаний | низкая | после завершённых подзадач |
| Context editing API | программная вставка/замена/удаление в окне | до +29% к качеству длинных запусков | зависит от поддержки провайдера | средняя | длинные агентские циклы, SDK-интеграции |
| Structured note-taking (файлы-заметки) | память вне окна, подтягивается по мере нужды | экономит повторные загрузки | рассинхрон файл↔реальность | низкая | всегда; между сессиями |
| Субагенты | изоляция контекста поиска/чтения | контекст главного агента минимален | доп. вызовы, латентность | средняя | исследование кода/веба, чтение документов |
| Prompt compression (LLMLingua и др.) | автосжатие промптов второй моделью | 4–20x на подгружаемых текстах | потеря точности, лишний вызов | средняя | RAG-подгрузки, большие документы |
| Контекст-кэш провайдера (prompt/context caching) | скидка на повторные входные токены | до 90% на стабильных префиксах | TTL, недоступен у роутеров | низкая | если провайдер/роутер поддерживает |
| Memory-системы (mem0/Zep/Letta/LangMem) | долгосрочная память между сессиями | экономит повторный контекст фактов | инфраструктура, латентность | средняя–высокая | постоянные пользователи/факты/граф |
| RAG/векторный поиск | точечная подгрузка релевантного | контекст ~размер ответа, а не корпуса | качество чанков/эмбеддингов | средняя | большие корпуса, документы |
| Фазовая работа с handoff-артефактами | сессии = фазы + файлы-переходы | сессии короткие, контекст свежий | требует дисциплины | низкая | лимиты роутера, цензура, большие проекты |
