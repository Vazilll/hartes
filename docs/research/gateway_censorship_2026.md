# Обход цензуры китайских AI-гейтвеев: легальные клиентские стратегии (2025–2026)

**Дата отчёта:** 17 августа 2026 г.
**Контекст:** у пользователя agentrouter.org — бесплатный китайский AI-роутер (модели claude-opus-4-8, gpt-5.6-sol). Длинные сессии (~45k токенов) детерминированно дают HTTP 500 с текстом `sensitive words detected`; короткие запросы работают.
**Статус источника:** все ключевые технические утверждения подтверждены чтением кода репозиториев (GitHub API / jsDelivr CDN) и официальных текстов НПА КНР; отдельные новостные факты 2025–2026 гг., которые не удалось верифицировать прямым fetch (поисковики блокировали скрейпинг), помечены явно.
**Фокус:** только легальные архитектурные приёмы на стороне клиента. Обфускация/шифрование запросов против фильтра шлюза — не работает технически и является нарушением ToS (см. §3, §5).

---

## TL;DR

1. Ошибка `500 sensitive words detected` — это **фильтр на уровне шлюза**, встроенный в форк-код new-api/one-api. Шлюз склеивает **все** сообщения истории (`meta.CombineText`) и до отправки апстриму прогоняет их через детерминированный Aho-Corasick-поиск по списку запрещённых подстрок. Совпадение → ошибка `sensitive_words_detected` → HTTP 500. Поэтому длинные сессии «ломаются»: любое историческое сообщение с триггером валит запрос снова, даже если текущий промпт чист.
2. Фильтр **можно полностью отключить/настроить на СВОЁМ инстансе** new-api: при пустом списке слов проверка вообще не выполняется (`if len(setting.SensitiveWords) == 0 { return false, nil }`), плюс есть флаги `CheckSensitiveEnabled` / `CheckSensitiveOnPromptEnabled` / `StopOnSensitiveEnabled` и админ-страница настроек. На чужом инстансе (agentrouter.org) вы этого сделать не можете — там свой список в БД оператора.
3. **Разбиение запроса и шифрование не помогают:** шлюз читает plaintext JSON до апстрима; шифровать поле `content` невозможно (сервер ждёт валидный текст), а обфускация — это уже обход технических мер (нарушение ToS, в юрисдикции КНР — правонарушение). Разбиение лишь статистически снижает вероятность совпадения подстроки в одном запросе.
4. **Реалистичные легальные стратегии:** (а) self-hosted new-api (или LiteLLM) на VPS вне Китая с западными upstream (OpenRouter/Anthropic/OpenAI/DeepSeek) — радикальное решение, ~€4–7/мес за VPS + реальные цены API; (б) клиентский прокси с суммаризацией истории («последние N сообщений + summary») — резко сокращает объём сканируемого текста; (в) локальный скринер триггеров с переписыванием собственного текста до отправки.
5. **Почему провайдер обязан фильтровать:** нормативные акты КНР прямо требуют «техническими или ручными средствами проверять входные данные и синтезированный результат» (ст. 10 深度合成规定), прекращать генерацию незаконного контента (ст. 14 生成式办法), вести логи ≥6 мес (ст. 9 标识办法, 2025-09-01). Детерминированный keyword-фильтр — самая дешёвая форма выполнения этих требований.

## 1. Как устроены new-api / one-api: где живёт фильтр чувствительных слов

### Архитектура
- **one-api** (songquanpeng/one-api, 36 425★, MIT) — оригинальный шлюз: единый OpenAI-совместимый API поверх множества провайдеров. В его кодовой базе **фильтра чувствительных слов нет вообще** (проверено по полному дереву файлов: ноль упоминаний `sensitive`/`敏感`). Пользователи просили добавить фильтр — issue #663 «请求添加敏感词过滤功能».
- **new-api** (QuantumNous/new-api, ранее Calcium-Ion/new-api; 45 371★, AGPL-3.0, последний push 15.08.2026) — самый популярный форк. Именно в new-api появилась полноценная подсистема чувствительных слов. Бесплатные китайские роутеры типа agentrouter.org обычно работают на new-api (или его fork-ах) с **собственным заполненным списком слов в БД оператора** — поэтому у них фильтр активен, хотя в исходниках репо по умолчанию стоит заглушка-слово `test_sensitive`.

### Код, который это делает (цитаты из main, QuantumNous/new-api)

**Точка принятия решения — `controller/relay.go`** (сканируется весь запрос до вызова апстрима):

```go
needSensitiveCheck := setting.ShouldCheckPromptSensitive()
...
if needSensitiveCheck && meta != nil {
    contains, words := service.CheckSensitiveText(meta.CombineText)   // ВЕСЬ текст запроса (все сообщения)
    if contains {
        logger.LogWarn(c, fmt.Sprintf("user sensitive words detected: %s", strings.Join(words, ", ")))
        newAPIError = types.NewError(err, types.ErrorCodeSensitiveWordsDetected)
        return   // запрос НЕ уходит апстриму
    }
}
```

**`service/sensitive.go`** — точная строка ошибки и логика:

```go
func CheckSensitiveMessages(messages []dto.Message) ([]string, error) {
    ...
    if ok, words := SensitiveWordContains(m.Text); ok {
        return words, errors.New("sensitive words detected")   // <-- та самая фраза
    }
    ...
}

func SensitiveWordContains(text string) (bool, []string) {
    if len(setting.SensitiveWords) == 0 {   // <-- ПУСТОЙ СПИСОК = ФИЛЬТР ВЫКЛЮЧЕН
        return false, nil
    }
    ...
    checkText := strings.ToLower(text)       // регистронезависимо
    return AcSearch(checkText, setting.SensitiveWords, true)  // Aho-Corasick, подстрочный поиск
}
```

**`setting/sensitive.go`** — управление:

```go
var CheckSensitiveEnabled = true
var CheckSensitiveOnPromptEnabled = true     // проверка входа
//var CheckSensitiveOnCompletionEnabled = true   // проверка выхода — закомментирована
var StopOnSensitiveEnabled = true            // true = «стоп» (->ошибка 500); false = замена слов
var SensitiveWords = []string{ "test_sensitive" }  // заглушка; реальный список приходит из настроек БД
```

**HTTP-статус — `relaykit/types/error.go`:** `ErrorCodeSensitiveWordsDetected = "sensitive_words_detected"`; конструктор `NewError` по умолчанию ставит `StatusCode: http.StatusInternalServerError` (500) — поэтому клиент видит именно 500, а не 400.

**Ответная (выходная) фильтрация:** в сервисном слое есть `SensitiveWordReplace` (заменяет совпадения на `**###**`), но в текущем main проверка выхода закомментирована, а при `StopOnSensitiveEnabled=true` генерация просто прерывается ошибкой. Т.е. режимы: **стоп (по умолчанию)** или **замена**.

### Что именно сканируется — и почему «ломаются» длинные сессии
- Проверяется **весь массив `messages[]` за один запрос** (вся пересылаемая история чата, объединённая в `CombineText`), а не только последнее пользовательское сообщение.
- Шлюзы OpenAI-совместимых API пересылают всю историю при каждом ходе. Значит, в сессии на 45k токенов шанс, что **хотя бы одно** историческое сообщение содержит триггер, близок к 100%. Как только триггер туда попал — **каждый следующий запрос** детерминированно возвращает 500, даже если новый текст чист. Это объясняет симптом пользователя: короткие запросы работают, длинные — детерминированный 500. (Размер тела тут ни при чём: лимит `MAX_REQUEST_BODY_MB=32` дал бы 413, а не 500.)

### Можно ли отключить/настроить на своём инстансе — ДА, тремя способами
1. **Пустой список слов:** `SensitiveWordContains` сразу возвращает `false` при пустом списке → проверка де-факто выключена.
2. **Флаги:** `CheckSensitiveEnabled = false` или `CheckSensitiveOnPromptEnabled = false` (в настройках/коде) полностью отключают проверку входа.
3. **Админ-панель:** в дереве репозитория есть страница `web/src/pages/Setting/Operation/SettingsSensitiveWords.jsx` — редактирование списка слов (по строкам) через UI; также можно править БД (SQLite/MySQL).
4. Правка исходников (Go) тривиальна, но при публичной раздаче AGPL-3.0 обязывает публиковать изменения.

**Важно:** всё это относится только к **вашему** инстансу. На чужом (agentrouter.org) список слов в БД оператора недоступен для изменения; «500 sensitive words detected» останется до тех пор, пока вы шлёте туда триггерный контент.

## 2. Self-hosted new-api: как поднять, какие провайдеры цепляются, стоимость

### Требования и установка (из README main)
- **Система:** 64-bit (amd64/arm64). **База:** SQLite по умолчанию (в Docker монтируйте `/data`) или MySQL ≥5.7.8 / PostgreSQL ≥9.6. **Контейнеры:** Docker / Docker Compose.
- **VPS:** хватает 1–2 ГБ RAM (лёгкий Go-бинарник + база); ориентир ~€4–7/мес (например, Hetzner CX22/CPX11: https://www.hetzner.com/cloud/; аналоги у DigitalOcean/Vultr). Для личного использования хватит самого дешёвого тарифа.
- **Docker (SQLite):**
  ```bash
  docker run --name new-api -d --restart always \
    -p 3000:3000 -e TZ=Asia/Shanghai \
    -v ./data:/data \
    calciumion/new-api:latest
  ```
  Или `git clone https://github.com/QuantumNous/new-api.git && docker-compose up -d`.
- **Ключевые env:** `SESSION_SECRET` (обязателен для multi-node), `SQL_DSN`, `REDIS_CONN_STRING` (опц.), `MAX_REQUEST_BODY_MB` (по умолч. 32), `STREAMING_TIMEOUT` (300 с).
- Документация: https://www.newapi.ai/en/docs (бывший docs.newapi.pro), раздел установки https://www.newapi.ai/en/docs/installation.

### Подключение провайдеров (каналы)
В new-api **нативные адаптеры** для ~35 типов каналов, включая западные:
- **OpenAI** (прямой ключ), **Anthropic Claude** (прямой ключ), **Google Gemini**, **xAI**, **Perplexity**, **Cohere**, **Mistral**, **AWS Bedrock**, **Azure**, **Vertex**;
- **OpenRouter** — отдельный нативный канал (`relay/channel/openrouter/`, модели авто-синкаются через их API); один ключ OpenRouter → доступ ко всем моделям всех провайдеров;
- **DeepSeek** — нативный канал (дешёвый китайский API; у него собственный, более мягкий фильтр на стороне модели — но это не гейтвей-фильтр);
- Китайские: Zhipu (GLM), Qwen (通义), Wenxin (文心), Xunfei (讯飞), Doubao (豆包), 360, Tencent и др.

### Сложность и подводные камни
- **Сложность: низкая** (для разработчика): одна docker-команда + создание каналов в веб-панели (тип канала, base_url, ключ). Полноценная панель: токены пользователей, лимиты, квоты, логи, стриминг.
- **Нужно:** платёжная карта для регистрации в западных API и пополнения баланса; ключи upstream.
- **Лицензия:** new-api — AGPL-3.0 (при публичном оказании услуг подключённым клиентам нужно публиковать изменения; для личного/корпоративного использования ок); one-api — MIT.
- **Upstream ToS:** прямые ключи Anthropic/OpenAI предназначены для личного использования; перепродажа третьим лицам запрещена их условиями. Для раздачи нескольким пользователям корректнее OpenRouter (позволяет прокси-использование) или официальные enterprise-договорённости.
- **Альтернатива без китайского кода:** **LiteLLM** (BerriAI/litellm, 56 535★) — лёгкий прокси-в-одну-команду, OpenAI-совместимый, поддержка OpenAI/Anthropic/OpenRouter/DeepSeek/Gemini: https://github.com/BerriAI/litellm, https://docs.litellm.ai.

На своём инстансе с западными upstream список чувствительных слов вы просто не заполняете (или очищаете) — китайский гейтвей-фильтр исчезает полностью. Обязательства КНР по фильтрации к вам как к частному лицу вне юрисдикции КНР не применяются (см. §5).

## 3. Подмена форматирования: разбиение на части / шифрование — честная оценка

**Вывод: не работает, и вот почему.**

1. **Шифрование/обфускация содержимого — технически невозможно в рамках API.** Шлюз принимает JSON (OpenAI Chat Completions / Claude Messages) и должен передать модели осмысленный текст поля `content`. Зашифровать/закодировать его (base64, XOR, шифр) = отправить модели мусор: она не поймёт запрос. Обфускация «слов» (вставка пробелов/спецсимволов между буквами) — это уже попытка обойти техническую меру модерации, а не легальный приём (нарушение ToS; в КНР — нарушение ст. 27 Закона о кибербезопасности / ст. 272 УК КНР).
2. **Разбиение запроса на части** уменьшает объём текста в одном запросе → статистически ниже шанс совпадения подстроки. Но:
   - шлюз сканирует **весь `messages[]`**, включая старые ходы — разбиение не спасает от триггера, уже засветившегося в истории;
   - фильтр **детерминированный** (Aho-Corasick, подстрочный, регистронезависимый): если подстрока есть — 500 гарантирован, «повезёт/не повезёт» не бывает;
   - чат теряет контекст при жёстком разбиении.
3. **Единственное, что честно работает на стороне клиента, оставаясь в рамках API:**
   - не отправлять триггерные подстроки вообще (переписывание своего текста до отправки — легально, см. §4.2);
   - не отправлять много контекста (суммаризация истории, §4.1);
   - сменить шлюз/провайдера (§2, §4.3–4.4).

Никакой «упаковки» запроса, которая легально обошла бы текстовый фильтр чужого китайского гейтвея, не существует — фильтр стоит до модели, снаружи вашего контроля.

## 4. Альтернативы на стороне клиента (легальные, архитектурные)

### 4.1 Локальный прокси с суммаризацией истории (chunking)
**Схема:** клиент/агент → local proxy → китайский роутер (или сразу западный upstream).
Прокси хранит историю у себя и в каждый запрос отправляет: последние K сообщений (например, 8–12) + сжатый summary более ранних. Summary формируется отдельным дешёвым вызовом той же модели (например, deepseek-v4-flash, ~$0.08/M входных токенов).
- **Эффект:** объём сканируемого текста падает на порядок; если summary и окно не содержат триггеров — 500 исчезает. Ограничение: если тема сама по себе «чувствительная», summary может содержать триггерные слова — фильтр это поймает. Это **сокращение поверхности**, а не обход.
- **Бонус:** экономия токенов и денег, ускорение.
- **Минусы:** потеря деталей старой истории, +1 латентный вызов на суммаризацию, инженерия (прокси ~100–200 строк на Python/LiteLLM с кастомным режимом).

### 4.2 Клиентский скринер триггеров (до отправки)
- Локально, до HTTP-вызова, проверяем текст по списку подстрок и **переписываем/перефразируем** рискованные фрагменты (синонимы, обобщения, разбиение на отдельные запросы по темам).
- Список триггеров можно нарабатывать эмпирически (бинарный поиск по ответам API: шлёте тестовые фразы и смотрите на 500). Это законно (вы исследуете публичный API), но: (а) может нарушать ToS роутера; (б) список оператора может меняться; (в) потратите квоту. Описание методики — в отчёте как «экспериментальная», без гарантий.
- **Важно:** это обработка **собственного** текста до отправки — юридически чисто (не вмешательство в чужую систему); риск — только ToS и возможная потеря смысла.

### 4.3 Смена шлюза: прямые официальные API
Anthropic / OpenAI / OpenRouter / DeepSeek напрямую (без китайского роутера). Никакого китайского гейтвея → нет его фильтра → нет 500 в принципе. Цена = реальная стоимость API (см. таблицу §2). Бесплатный роутер заменяется платным: от ~$0.08/M (deepseek-flash) до $5/$30 M (gpt-5.6-sol, claude-opus-4.8).

### 4.4 Self-hosted шлюз на VPS вне Китая
Ваш инстанс new-api/LiteLLM (см. §2) с западными upstream: сохраняете единый OpenAI-совместимый API для всех своих агентов, получаете квотирование, логи, группировки; фильтр чувствительных слов — ваш выбор (по умолчанию выключен). Рекомендуемый вариант для продолжения работы с claude-opus-4.8 / gpt-5.6-класс моделями без цензуры.

## 5. Политика и риски: что закон требует от провайдеров и почему 500 детерминирован

### Нормативная база КНР (проверенные тексты)
1. **《网络安全法》(Закон о кибербезопасности, 2017)** — ст. 12, 47: платформы обязаны пресекать распространение незаконной информации.
2. **《网络信息内容生态治理规定》(Положение об экологическом управлении сетевым контентом, 2020-03-01)** — http://www.cac.gov.cn/2019-12/20/c_1578375159509309.htm — ст. 6 (запрещённая информация), ст. 9 (обязанность платформ: модерация публикаций, реальный мониторинг, реагирование), ст. 34 (меры к нарушителям).
3. **《互联网信息服务深度合成管理规定》(Положение о сервисах глубокого синтеза, 2023-01-10)** — https://www.cac.gov.cn/2022-12/11/c_1672221949354811.htm — **ст. 7** (ответственность за информационную безопасность: регистрация пользователей, аудит, реагирование), **ст. 10: «принимать технические или ручные меры для проверки входных данных пользователей и синтезированных результатов»** — прямое правовое основание фильтров входа и выхода, ст. 16 (логи, метки), ст. 18 (запрет удалять метки).
4. **《生成式人工智能服务管理暂行办法》(Временные меры управления сервисами генеративного ИИ, действуют с 2023-08-15)** — http://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm — ст. 4 (служить социалистическим ценностям), ст. 9 (ответственность как производителя контента), ст. 12 (маркировка по правилам глубокого синтеза), **ст. 14: при обнаружении незаконного контента — немедленно прекратить генерацию/передачу и устранить его**, ст. 17 (для сервисов, влияющих на общественное мнение: оценка безопасности + алгоритмическая регистрация 备案), ст. 20 (экстерриториальность), ст. 21 (санкции).
5. **《人工智能生成合成内容标识办法》(Меры по маркировке ИИ-контента, действуют с 2025-09-01)** — https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm (зеркало: https://www.gov.cn/zhengce/zhengceku/202503/content_7014286.htm) — ст. 5 (скрытая метка в метаданных файлов), ст. 9 (при выдаче контента без видимой метки — хранить логи получателей **не менее 6 месяцев**), ст. 13 (санкции).
6. **TC260-003《生成式人工智能服务安全基本要求》(2024-03-01)** — технический стандарт для оценки безопасности генеративных сервисов (обучающие данные, безопасность модели, **безопасность контента**, требования к фильтрации) — вторичный источник: https://zh.wikipedia.org/wiki/生成式人工智能服务管理暂行办法 (там же: по состоянию на конец 2025 г. — 748 сервисов с нац. 备案 и 435 локальных регистраций; анализ Carnegie Endowment о том, что контентные обязательства исполняются строже всего).
7. В 2025 г. принят **обязательный госстандарт GB 45438-2025 «Базовые требования безопасности услуг ИИ»**, конкретизирующий требования к контент-безопасности (детали и точные даты не удалось верифицировать в рамках отчёта — поисковые сервисы блокировали ботов). Проект **Закона КНР об искусственном интеллекте** находился в 2025–2026 гг. на стадии законодательного процесса в ПК ВСНП (по сообщениям прессы).

### Почему фильтр детерминированный и почему 500
- **Юридически** провайдер обязан «иметь технические меры» проверки входа/выхода (ст. 10 深度合成规定) и «прекращать генерацию» (ст. 14 生成式办法). Самая дешёвая и контролируемая мера — детерминированный keyword-фильтр до вызова модели + пост-фильтр вывода. Семантическая (ML) модерация дороже, менее предсказуема для аудита и не обязательна.
- **Технически** фильтр в new-api построен на Aho-Corasick-автомате: поиск подстрок, регистронезависимый, чисто детерминированный. Один и тот же вход → один и тот же результат всегда. Это вписывается в многолетнюю практику китайской интернет-цензуры, построенной на keyword-фильтрации (классическое исследование: King, Pan, Roberts, «How Censorship in China…», American Political Science Review 107(2), 2013, DOI 10.1017/S0003055413000014).
- **500 вместо 400** — особенность реализации: new-api релеит эту ошибку как «внутреннюю ошибку релея» с кодом `sensitive_words_detected` (дефолтный статус `NewError` — `http.StatusInternalServerError`), поэтому клиент видит HTTP 500 с телом-ошибкой в OpenAI-стиле.

### Риски пользователя
- **Для клиента вне КНР:** переписывание собственных текстов, суммаризация, смена провайдера — законны. «Обход» технических мер модерации чужого сервиса (обфускация, шифрование, подмена протокола) — нарушение ToS роутера, риск блокировки аккаунта/ключа; в юрисдикции КНР — дополнительно правонарушение.
- **Для оператора self-hosted в КНР:** при оказании услуг «публике КНР» обязательны 备案, оценка безопасности, реальная идентификация пользователей, фильтры, логи ≥6 мес, маркировка — new-api прямо предупреждает об этом в README («filing, licensing, content safety, real-name verification, log retention…»). Вне КНР эти обязанности не применяются; остаются только ToS upstream (запрет перепродажи прямых ключей).
- **Юридический статус обхода в КНР:** создание/использование программ для обхода мер защиты сетей — ст. 27 Закона о кибербезопасности; вмешательство в компьютерные системы/данные — ст. 272 УК КНР. Настоятельно не рекомендуется.

## 6. Реалистичные варианты для клиента — сравнение и рекомендация

| Вариант | Что даёт | Стоимость | Сложность | Риски |
|---|---|---|---|---|
| **A. Продолжать через agentrouter.org** с клиентским прокси (последние N + summary) и локальным скринером | 500 резко реже; модели те же, бесплатно | 0 + время на прокси | Средняя | Не гарантирует чистоты; ToS-хрупкость; потеря деталей истории |
| **B. Прямые официальные API** (Anthropic/OpenAI/OpenRouter/DeepSeek) | Цензуры гейтвея нет вообще | От ~$0.08/M (DeepSeek-flash) до $5/$30 M (флагманы) | Низкая | Платная; нужна карта |
| **C. Self-hosted new-api / LiteLLM на VPS вне Китая + OpenRouter/Anthropic/DeepSeek** | Все модели без фильтра, свой контроль, единый API, квоты | VPS ~€4–7/мес + реальные цены API | Средняя (1 вечер) | AGPL-при публичной раздаче; ToS upstream при перепродаже |
| **D. Самостоятельно хостить open-weight модели** (DeepSeek R1/V4, Qwen) на своей GPU-аренде | Полная независимость, фильтр = ваш выбор; open-weight версии можно цензурой не дополнять (см. en-wiki DeepSeek: самост. хостинг убирает выходную цензуру) | GPU-аренда (десятки $/мес и выше) | Высокая | Модели слабее claude-opus/gpt-5.6-класса; инфраструктура |

### Рекомендация (исходный кейс: нужны claude-opus-4.8 / gpt-5.6-sol, длинные сессии, бесплатный роутер)
1. **Краткосрочно:** поставить локальный прокси с суммаризацией истории (вариант A) — быстро снимает основную массу 500-ошибок, пока идёт миграция.
2. **Основное решение — вариант C:** поднять new-api (или LiteLLM) на VPS вне Китая (~€5/мес), каналы: OpenRouter (сразу все модели, включая claude-opus-4.8 и gpt-5.6-sol) + DeepSeek (для дешёвых суммаризаций/черновиков). Фильтр чувствительных слов не настраивать (пустой список). ~1 час на всё.
3. **Не тратить время** на шифрование/обфускацию запросов и «разбиение форматирования» — не работает и нарушает ToS.
4. Если бюджет нулевой и готовы к ограничениям — вариант A + периодическая суммаризация вручную; 500 останутся для тем с триггерными словами.

## Методология и ограничения
- Технический раздел построен на прямом чтении кода main-веток new-api/one-api (GitHub API + jsDelivr CDN; файлы сохранены локально во время исследования).
- Тексты НПА скачаны с официальных страниц CAC/gov.cn и прочитаны полностью (статьи процитированы по номерам).
- Поисковые сервисы (DDG, Bing RSS, Mojeek, Qwant, Sogou) блокировали программный доступ; браузерный инструментарий в среде был недоступен, поэтому часть новостных фактов 2025–2026 гг. (даты версий GB 45438-2025, статус Закона об ИИ) не удалось верифицировать по первоисточнику — в тексте они помечены как «по сообщениям прессы» и не используются как ключевые аргументы.
- Ключевые аргументы (механика фильтра, отключаемость, правовое основание, детерминизм 500) полностью подтверждены первоисточниками.
